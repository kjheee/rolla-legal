# Rolla 공개 정책·지원 사이트

앱 소스·자격 증명·개인정보·운영 로그를 포함하지 않는다. 앱 저장소의 `docs/legal`은 과거 초안이며 이 저장소가 공개 문서 원본이다.

## 공개 경로

기준 주소: https://kjheee.github.io/rolla-legal/

- `/terms/`: 이용약관, 2026-10-20 시행
- `/privacy/`: 개인정보 처리방침 출시 검토본. 외부 처리·로그 파기 조건을 닫기 전 정식 정책으로 표시하지 않는다.
- `/community/`: 금지 콘텐츠·아동 안전·신고·제재·이의제기
- `/support/`: 운영자·개인정보 책임자·지원 이메일의 단일 원본
- `/delete-account/`: 앱 내 삭제와 앱 재설치 없는 이메일 삭제 요청

GitHub Pages의 main 루트 Jekyll 배포를 사용한다. 정책 변경 후 앱의 `LEGAL_VERSION`, 링크, 동의 흐름과 기존 가입자에 대한 변경 고지·재동의 필요성을 함께 검토한다. 개인정보 처리방침까지 확정되기 전에 앱의 공통 동의 버전을 정식 출시 버전으로 올리지 않는다.

## 2026-10-20 확인 결과

- 운영자·개인정보 책임자 및 지원 이메일은 기존 공개 문서의 확정 값을 유지했다.
- Supabase CLI와 대시보드에서 Rolla DB·Storage의 서울 리전(ap-northeast-2), 조직 Free 플랜을 확인했다. 리전은 모든 처리의 국내 한정을 뜻하지 않는다.
- 공식 Free 요금표에는 자동 백업이 포함되지 않는다. 운영자의 수동 백업은 별도 관리 대상이다.
- 기존 계정 삭제·Storage 정리 기능은 앱 운영 문서에 배포 및 합성 계정 검증 기록이 있다. Apple 실제 권한 해지·소셜 재가입·실기기 정리 검증을 대체하지 않는다.
- GitHub Pages 비활성화로 발생한 404를 해결했다. `cb2be76` 배포 성공과 공개 문서 6개 경로의 HTTP 200을 확인했다.
- 사용자 승인: 신고·문의·Discord 사본은 처리 완료 후 1년 이내, 수동 백업은 생성 후 30일 이내 삭제. 탈퇴 시 관련 개인정보는 앞당겨 파기. 최종 공개일을 시행일로 사용한다.

## 초기 출시의 최소 범위

기존 계정 삭제 기능과 운영자의 수동 처리로 시작한다. 별도 자동 파기 시스템·관리자 도구 개발이나 외부 업체 내부 시스템 감사, 모든 장애 상황의 사전 시험을 출시 조건으로 두지 않는다. 실제 삭제와 정확한 고지는 계속 수행해야 한다.

- [x] 운영자 김정희를 수동 파기 담당자로 두고 아래 대상·시점·방법을 정했다. 이 체크는 운영 기준 확정이며 실제 데이터 파기 완료를 뜻하지 않는다.
- [x] 사용자 확인: 배포본의 신고·차단·탈퇴·문의 수신 및 스토어 정책 URL 등록 완료. 에이전트가 직접 검증한 결과로 기록하지 않는다.
- [ ] 처리방침 작성에 필요한 실제 로그 보유 기간과 외부 서비스의 처리 항목·위탁·국외 이전 사항을 공급자 문서·계약·서비스 설정에서 확인한다. 알 수 없는 값을 추정해 채우지 않으며, Free 플랜의 조회 가능 기간을 모든 사본의 완전 삭제 시점으로 간주하지 않는다.
- [ ] 확인한 사실을 처리방침에 반영해 검토 표시를 제거하고 시행일·앱 동의 버전·지원 이메일을 정렬한다. 기존 가입자 변경 고지·재동의 필요성과 스토어 개인정보 양식의 일치도 검토한다.

기존의 출시 전 전체 파기 검증·실행 기록 확보 항목은 권장 점검으로 옮겼다. 운영 중 기한이 도래하거나 삭제 요청이 있으면 실제로 처리하고 그 결과를 확인해야 한다.

## 승인된 보관 기준의 수동 파기 절차

담당자는 운영자 김정희다. 별도 시스템 개발 없이 접근 제한된 간단한 대장에 대상 ID·처리 완료 시각 또는 백업 생성일·파기 기한·저장 위치·처리 결과를 기록한다. 원문·사진·비밀번호·토큰을 이 저장소에 남기지 않는다. 1년·30일은 법정 의무 기간이 아닌 승인된 최대 운영 기간이며, 개인정보가 더 이상 필요하지 않으면 그 전에 파기한다.

1. 매일 접수·미처리 상태를 확인하고 처리 완료 시점을 기록한다. 신고는 24시간 내 검토 시작을 목표로 한다.
2. 처리 완료 후 1년이 도래하기 전에 신고·문의 DB 행, 첨부 Storage 객체, Discord 메시지·첨부, 관련 이메일 사본을 함께 파기한다. DB 행만 지우고 파일을 남기지 않는다.
3. 계정 삭제 완료를 확인할 때 작성자·신고 대상 등 관련 개인정보가 남은 외부 사본과 백업을 함께 확인한다. 법적 보존 근거가 없다면 조기 삭제한다. 공유 백업에서 개별 삭제가 어렵다면 그 백업을 폐기하거나 해당 정보를 제거한 사본으로 교체한다.
4. 수동 백업은 생성일과 30일 이내 파기 기한을 기록하고 만료 전에 삭제한다. 새 백업을 만들었다고 이전 백업이 삭제된 것으로 간주하지 않는다.
5. 파기 실패는 재시도 대상으로 남기고, 삭제 대상·각 저장 위치의 결과를 확인한 뒤 완료 처리한다. 복원 시 이미 삭제한 계정 데이터가 되살아나지 않는지도 확인한다.

이 문서는 실행 절차이며 실제 파기 완료 기록은 아니다. 데이터 삭제 작업은 별도 승인과 범위 확인을 거쳐 수행한다.

## 권장 점검과 후속 개선

- 대표적인 테스트 계정 한 건으로 서버 삭제와 외부 사본의 수동 삭제 경로를 따라가 본다. 운영 실수를 줄이기 위한 권장 점검이며 전수 시험을 요구하지 않는다.
- 이메일 요청의 본인 확인, Apple 권한 해지·소셜 재가입 등 세부 시나리오는 사용자 확인 범위와 구분해 필요한 경우 점검한다.
- 처리량이 늘거나 기한 관리가 어려워지면 알림·자동 파기·관리자 화면을 추가한다. 초기 출시의 선행 개발로 요구하지 않는다.
- 공급자 내부 시스템은 직접 감사 대상으로 삼지 않는다. 공개 문서·계약·설정으로 확인되지 않는 고지 항목은 해당 공급자에 확인한다.
